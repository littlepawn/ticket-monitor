# 火车票余票监控（Docker · NAS 可用）

一个「只管查余票 + 推送通知」的小服务：**管理页面配参数，发现余票就推手机**。

**不登录、不带 Cookie、不占座、不下单、不抢票，也不做任何验证码/设备指纹/代理池对抗**——
所以没有被封的账号，只有一台在低频率下替你盯着余票的服务。

## 功能

- 管理页面配参数：出发站 / 到达站 / 日期 / 车次（可选）+ 席别偏好（多选）
- **不填车次时可按「出发时间段 + 票价区间」筛选**，避免被无关车次刷屏
- 站名自动补全（支持中文、拼音、简拼、三字码，内置 3404 个车站）
- 余票看板：每个任务展示各席别「有票 / 候补 / 无票」、逐车次明细与最低票价
- **总览页卡片可点击查看详情**：有票任务一眼看到车次、时刻、有票席别与票价；支持键盘 Enter 与 Esc 关闭
- **每个席别显示自己的票价**（不是共用一个最低价），且不产生额外请求
- **点击车次查看经停站**：站序、到达/发车时刻、停留时间，始发与终到有标记
- **席别用 15 色小圆点区分**，文字保持中性色；有票=实心、无票=空心。价格用中性灰，不抢眼
- **有票车次自动排在最前**（其次按余票张数与发车时间），避免有票的车被埋在十几行之后
- **站名匹配方式可选**：默认「精确匹配」只查所选车站；可切为「模糊匹配」包含同城其它站
- **四个筛选维度**：车次 / 出发时段 / 票价区间 / 历时，各自独立、可组合、可全不开
- **日期已过期的任务会自动置灰并停止监控**，修改日期后才能重新启用
- **修改任务条件后立即重新查询**，不会出现"新标题 + 旧目的地数据"的错配
- 多渠道路由：Server 酱 / Bark / 企业微信 / 钉钉 / Telegram / PushPlus / ntfy / 自定义 Webhook
- 命中即推、重复命中不刷屏、余票消失可推恢复；支持静默时段
- 查询节奏保守可调，撞到 `429/403/412` 自动指数退避（最长 30 分钟），不会持续冲接口
- 配置导入导出、访问令牌（可选）、SSE 实时刷新、Docker 健康检查

## 界面说明

**席别用彩色小圆点区分，文字保持中性色**：

| 席别 | 圆点颜色 |
|---|---|
| 商务座 | 紫 |
| 特等座 / 优选一等座 | 品红 / 洋红 |
| 一等座 | 蓝 |
| 二等座 | 青 |
| 软座 | 天蓝 |
| 高级软卧 / 软卧 / 硬卧 | 深棕 / 琥珀 / 金 |
| 动卧 / 一等卧 / 二等卧 | 黄绿 / 橙 / 玫红 |
| 硬座 / 无座 / 其他 | 石板 / 浅石板 / 石灰 |

共 15 色，覆盖官方全部席别；未知席别兜底到「其他」色。

**关键设计：颜色只落在 8px 的圆点上，文字一律中性色。**
早先试过「整块文字换色」和「图标」，两条路都不理想——整块换色时一行里十几个彩色字互相干扰，
图标则因 15px 尺寸下细节难以辨认。圆点占位极小，颜色再多也不会糊成一片。
有票=实心圆点，无票=空心圆点。

**价格用中性灰色**：价格不是需要抢眼的信息，整列几十个绿色数字非常费眼，
绿色只留给「余票状态」这类真正需要一眼看到的信号。

**表格排序**：有票车次优先（张数多的更前），其次按发车时间。不排序时表格按发车时间排，
当勾选的席别只有普速车才有时（如硬卧/硬座），有票的车会被埋在十几行高铁之后。

## 席别票价与经停站

**每个席别各自的票价**：表格中每个席别列下方直接显示该席别的票价（如「商务座 9 / ¥2315」），
而不是所有席别共用一个最低价。票价来自余票响应里的 `yp_info_new`，**不产生任何额外请求**。

> 注意：票价表是该车次的**报价表**，与余票状态相互独立——某席别显示「无票」时仍可能有报价
> （实测 55 个车次里有 3 个如此），这是正常的，页面照常显示价格。

**经停站**：点击表格里的车次号（蓝色虚线下划线）弹出该车次的完整经停站：

| 列 | 说明 |
|---|---|
| # | 站序 |
| 车站 | 站名，始发站标「始发」、终到站标「终到」 |
| 到达 / 发车 | 该站到发时刻；始发站到达显示 `-` |
| 停留 | 停站时长，始发与终到显示 `-` |

实现要点：

- **按需查询，不参与轮询**。经停站接口是「每个车次一次请求」，若放进轮询，55 个车次就会变成
  55 倍请求量，直接违背低打扰约束。因此只在用户点击时拉取（代码里有测试断言引擎不得调用它）
- **结果缓存 6 小时**（内存 LRU，最多 300 条），反复查看同一车次不会重复请求
- 请求只传任务 id 与车次内部编号，日期与站点码由服务端从任务自身解析，避免前端拼参数去打任意区间

## 站名匹配：精确 vs 模糊

**关键背景：12306 按「城市」返回车次，不是按车站。** 请求「盐城」会同时返回「盐城」和
「盐城大丰」的车次，于是一个车次会出现两次、到达时刻与历时都不同，看起来像重复 bug。

因此提供两种模式（创建/编辑任务页可选）：

| 模式 | 行为 |
|---|---|
| **精确匹配（默认）** | 只保留所选车站的车次。选「盐城」就只显示到「盐城」的车 |
| **模糊匹配** | 保留同城所有车站。选「盐城」会同时出现到「盐城大丰」的车次 |

实测「杭州西→盐城」：精确 10 个车次（全部到盐城，剔除 7 条同城其它站）；
模糊 17 个车次（含 3 个重复车次，到站为盐城大丰）。

## 筛选条件（四个维度，各自独立）

任务的过滤条件分四块，**每块独立开关：可以只开一个、可以任意组合、也可以全部不开**。同时开启时取交集（AND）。

| 条件 | 开关 | 说明 |
|---|---|---|
| 车次 | 填了即生效 | 逗号分隔，如 `G2,G4`。留空表示不限车次 |
| 出发时段 | 独立开关 | `HH:MM` 起止，支持跨午夜（如 `22:00` 至 `06:00`）。只填一端则只限制那一端 |
| 票价区间 | 独立开关 | 按勾选席别取**最低票价**比较，单位元。只填一端则只限制那一端 |
| 历时 | 独立开关 | 填 `4:30` 表示 4 小时 30 分；只填 `4` 表示 4 小时。只填一端则只限制那一端 |
| 席别偏好 | 始终生效 | 命中任一席别有票即推送；同时决定票价按哪些席别比价 |

设计要点：

- **四个维度互相叠加**，例如「限定 G2/G4 + 06:00–09:00 + ¥700 以内 + 6 小时内」会同时生效，而不是互相覆盖
- **关闭的维度完全不参与过滤**，且保存时会清掉该维度的残留值，避免"界面显示着却不生效"的误导
- 弹窗里关闭的开关会把对应输入框置灰并标注「未启用」；开了但没填值会提示「待填写」，保存时后端也会拒绝
- **不产生额外请求**：票价直接来自余票响应里的 `yp_info_new` 字段，已与官方 `queryTicketPrice` 接口逐项核对一致
- 没有票价数据的车次**不会**因价格被过滤掉；历时缺失的车次同样不参与历时判断，避免误杀
- 12306 用 `24:00` 表示当日末班（午夜发车），已按 00:00 归一到跨午夜区间
- 筛选把结果清空时会明确提示原因（并区分"筛选后无车次"与"确实无票"），不会让人对着 0 个车次猜
- 从旧版本升级时自动迁移：原来填过时段/票价的任务会被视为"已启用"，不会静默失效

## 页面实时性

- 状态经 SSE（`/api/stream`）实时推送，无需手动刷新
- **每轮调度结束都会推送一次状态**，即使这一轮完全没有事件（「无票」是最常见的正常结果，
  它不产生任何事件）—— 否则页面上的倒计时会停在 0、余票概览与车次数永远不更新
- 倒计时归零超过 5 秒仍未收到新状态时，前端会主动补拉一次
- SSE 断开时自动降级为 5 秒轮询，EventSource 重连成功后恢复推送
- 顶栏与统计卡的时钟用**浏览器本地时间**每秒走时，不依赖服务端推送
- 修改「查询间隔」会立即重排下一轮，不必等当前这一轮旧间隔走完

## 快速开始（NAS / 任意 Docker 主机）

```bash
# 1) 建数据目录（必须让容器用户可写，容器内 node 用户 uid=1000）
sudo mkdir -p /volume1/docker/ticket-monitor/data
sudo chown -R 1000:1000 /volume1/docker/ticket-monitor/data

# 2) 起服务（把 docker-compose.yml 里 ./data 改成上面的绝对路径）
docker compose up -d
```

打开 `http://NAS的IP:8080/` → 「监控任务」新增 → 「推送渠道」加一个 → 点「测试推送」确认能收到。

### 国内拉不到镜像时（推荐路径）

在能联网的电脑上打包好 tar，拷进 NAS 后 `docker load`：

```bash
bash scripts/pack-image.sh          # 产出 ticket-monitor-1.0.0.tar
```

NAS 上 SSH 执行：

```bash
sudo docker load -i /volume1/docker/ticket-monitor-1.0.0.tar
```

然后在 Container Manager → 映像 → 启动，映射端口 `8080`、装载路径 `/data`；
或用 `docker-compose.yml`（把 `image` 设为 `ticket-monitor:1.0.0`、注释掉 `build`）。

### 直接在 NAS 上构建

Container Manager 里「项目 → 新增」选本目录（含 `docker-compose.yml`）即可。
国内拉 `node:22-alpine` 可能超时，可在「注册表」里配置镜像加速，
或先 `docker pull docker.1panel.live/library/node:22-alpine` 再 `docker tag` 成 `node:22-alpine`。

## WebDAV 云端备份

把配置备份到坚果云 / Nextcloud / NAS 自建 WebDAV 等任意标准 WebDAV 服务，用于换机迁移与误删恢复。

**设置步骤**（页面「设置」→「WebDAV 云端备份」）：

1. 勾选「启用 WebDAV」，填地址、账号、密码（坚果云需用「应用密码」，不是登录密码）
2. 点「测试连接」确认通，再点「保存 WebDAV 设置」
3. 需要时点「立即备份」，或勾选「配置变更后自动备份」

**关键安全设计：密钥不上云。** 备份文件里的推送密钥与访问令牌一律写成 `******`；
WebDAV 密码本身也不会写进备份。恢复时自动用**本地已存的密钥**补回同 id / 同名渠道，
所以：

- 同一个实例：备份 → 恢复可完整还原（含密钥）
- **跨机器**：任务与设置可还原，但渠道密钥需要手工补填（页面会提示哪些渠道缺密钥）

**备份内容**：任务、推送渠道、全部设置（含筛选与节奏参数）。

**恢复是整体替换**（不是合并），风险高，因此做了三重保护：

- 恢复前会先把当前配置写成 `config-before-restore-<时间戳>.json` 留在数据目录，可手工回滚
- 页面二次确认，明确说明会覆盖当前配置
- 备份文件先过结构校验、任务与渠道逐条走与新建时相同的校验，任何一条不合法就中止恢复，不会把坏数据灌进运行时

**保留份数**：默认 20 份，超出的最旧备份自动删除（可调 1–100）。自动备份有 1 分钟去抖，
连续改配置只上传一次，避免把云端刷满。

**兼容性**：使用标准 WebDAV 方法（`OPTIONS` / `MKCOL` / `PUT` / `GET` / `PROPFIND` / `DELETE`），
零依赖实现。401/403/404/405/409 等状态码会翻译成可操作的中文提示（例如「部分网盘仅支持有限方法」）。

## 配置项（环境变量）

| 变量 | 默认 | 说明 |
|---|---|---|
| `PORT` | `8080` | 监听端口 |
| `DATA_DIR` | `/data` | 配置持久化目录（挂卷） |
| `TZ` | `Asia/Shanghai` | 镜像已内置 tzdata，日志与静默时段按此计算 |
| `LOG_LEVEL` | `info` | `debug` / `info` / `warn` / `error` |
| `AUTO_START` | `true` | `false` 时容器起来不自动轮询，需在页面手动启动 |
| `STATION_OFFLINE` | 未设 | `1` 时只用镜像内置车站表，完全不联网取车站数据 |

配置数据全部在 `$DATA_DIR/config.json`，备份这个文件即可。

## 推送渠道

| 类型 | 必填 |
|---|---|
| Server 酱 | SendKey（`SCT` 开头走 Turbo，`sctp…` 开头走 Server酱³） |
| Bark | Device Key（可改服务器地址） |
| 企业微信 | 群机器人 Webhook |
| 钉钉 | Webhook（+ 可选加签密钥） |
| Telegram | Bot Token + Chat ID |
| PushPlus | Token |
| ntfy | Topic（可改服务器地址，默认 ntfy.sh） |
| 自定义 Webhook | URL，POST JSON `{title, body, watchId, date, kind}` |

密钥只在服务端保存与使用；所有 API 响应与页面都把密钥显示为 `******`，
编辑时提交掩码值不会覆盖已存的真实密钥。

## 风控与合规边界

- 只调用官方公开的只读余票查询接口，全程不带登录态（显式发送空 `JSESSIONID`）
- 默认 900 秒一次 + 最多 120 秒随机抖动，串行查询避免并发叠加；间隔下限 60 秒
- 错误按次指数退避（1→2→4→8→16→30 分钟封顶），退避期间调度不发起请求
- 车站表优先在线获取，失败时回落到镜像内置副本，避免因外网抖动而失能
- 不提供、也不会加入：自动登录、自动下单、候补代提交、验证码识别、指纹伪装、代理池

## 本地开发

```bash
node src/server.js         # http://127.0.0.1:8080
node tests/run.js          # 离线单元测试 + 接口契约（不访问 12306）
node scripts/smoke.js      # 真实接口冒烟（会访问一次 12306 只读接口）
```

运行时零 npm 依赖，只用 Node 20+ 内置模块。

## 目录结构

```
src/client.js     12306 只读客户端：车站表、站名解析、余票查询与解析、命中判定
src/engine.js     调度与状态机：节奏抖动、命中去重、退避熔断、事件
src/notifier.js   8 种推送渠道适配 + 密钥掩码
src/server.js     HTTP 服务与 REST/SSE 接口
src/store.js      config.json 原子读写与损坏自愈
src/logger.js     环形日志缓冲（页面「事件与日志」读取）
public/           管理页面（零构建，原生 JS）
assets/           内置车站表（离线兜底）
```

## 接口速查

```
GET  /health                     健康检查（容器健康检查用）
GET  /api/state                  运行状态 + 任务快照 + 事件 + 日志
GET  /api/stream                 SSE 实时推送
GET  /api/config                 配置（渠道密钥已掩码）
GET  /api/stations?q=北京         站名搜索
POST /api/watches                新增任务
PUT  /api/watches/:id            修改任务
POST /api/watches/:id/check      立即查询单个任务
POST /api/check-all              立即查询全部任务
POST /api/settings               保存设置
POST /api/channels               新增渠道
POST /api/channels/:id/test      发送测试推送
POST /api/channels/test-draft    未保存的渠道也能测

```
